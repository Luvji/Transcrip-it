# TI-0012 — Ubuntu audio-capture feasibility spike

## Target environment

- Ubuntu 22.04.4 LTS, Linux 6.8, GNOME on X11.
- PulseAudio 15.99.1 with PipeWire 0.3.48 command-line tools available.
- Default microphone: `alsa_input.pci-0000_00_1f.3.analog-stereo`.
- Default system monitor: `alsa_output.pci-0000_00_1f.3.analog-stereo.monitor`.
- PulseAudio recording tools, FFmpeg 4.4.2, and Node.js 22 are available.
- Rust is not currently installed, so the spike uses dependency-free Node.js orchestration around PulseAudio's raw recorder.

## Scope

The spike lists recording sources and captures microphone audio, system audio, or both into separate PCM WAV tracks. Raw samples are divided at exact sample-count boundaries into independently playable chunks. WAV headers are refreshed while recording, so completed chunks and most of the current chunk remain readable after an interruption. An atomic `manifest.json` records the selected sources, capture settings, completion state, chunks, and diagnostics.

The explicit `--consent-confirmed` flag prevents accidental recording. Generated sessions default to the gitignored `recordings/` directory with owner-only directory permissions.

## Commands

```bash
npm run audio:devices
npm run audio:record -- --mode both --consent-confirmed
```

For a short validation capture:

```bash
npm run audio:record -- \
  --mode both \
  --duration 10 \
  --chunk-seconds 5 \
  --output recordings/smoke-test \
  --consent-confirmed
```

Stop an open-ended capture with `Ctrl+C`. The CLI closes the current WAV files and finalizes the session manifest.

## Feasibility decision

The target exposes both a microphone and an output-monitor source. A real five-second combined capture completed without process errors. Both tracks produced independently playable 48 kHz, 16-bit stereo PCM WAV chunks, exact full chunks were two seconds long, and FFmpeg decoded every generated file successfully.

The microphone took approximately 1.4 to 1.8 seconds longer than the system monitor to begin delivering samples after process startup. Source readiness, common session start, and track alignment therefore need explicit validation under TI-0013. Manual listening and longer recording scenarios remain part of testing rather than proof supplied by this automated smoke run.

## Failed separation review

Manual playback found system content in the microphone track. Host routing inspection confirmed that the microphone track used the physical `analog-input-internal-mic` port, the system track used the sink monitor, and no PulseAudio loopback or echo-cancellation module was loaded. The tracks were not digital duplicates, which is consistent with the internal microphone acoustically picking up laptop-speaker playback.

A controlled muted-speaker or headphone repeat can distinguish acoustic bleed from hardware-codec crosstalk, but it is diagnostic only and is not a user requirement. The supported speaker workflow needs an evaluated echo-cancellation path before the spike can be approved.

Headphones are not a release requirement. An experimental offline adaptive-filter output was compared with the raw microphone and failed review because speech became spread and unclear. That command has been removed from the supported CLI; the generated file remains only as failed experimental evidence. The replacement feasibility path is PulseAudio's WebRTC acoustic echo canceller, with automatic and reversible playback routing.

## WebRTC capture candidate

The `--echo-cancel` recording mode loads a temporary PulseAudio WebRTC echo-cancel source and sink in an explicit 48 kHz mono processing format. It makes the virtual sink the default, moves existing playback streams through it, records the echo-cancelled microphone, raw microphone, and virtual sink monitor, and restores the previous default and stream routes when capture ends.

```bash
npm run audio:record -- \
  --mode both \
  --duration 30 \
  --echo-cancel \
  --consent-confirmed
```

This path must be tested with laptop-speaker playback and near-end speech. An interrupted process normally restores routing through its signal handlers; a forced process kill can bypass cleanup and remains a recovery case to address before release.

## MVP decision

The WebRTC path is accepted for the initial MVP. It is substantially better than raw internal-microphone capture, but loud system playback can suppress local speech during double-talk. The application must recommend a headset or moderate speaker volume and clearly disclose this limitation before recording; a headset is not mandatory. Improved double-talk preservation is deferred to TI-0102 so it does not block a working MVP.
